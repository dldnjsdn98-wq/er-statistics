# 검증 계획 및 후속 연결 체크

## 자동 검증

도메인 테스트는 고정 시각과 소수의 명확한 경기를 사용한다. 현재 날짜에 따라 결과가 흔들리지 않게 시간을 주입한다.

1. KST 단일 날짜 시작 경계는 포함하고 종료 다음날 자정은 제외한다. 월말·연말·윤년·잘못된 날짜·역전 범위를 검증한다. 실행 머신 TZ=UTC와 다른 TZ에서도 결과가 같다.
2. A와 B를 선택한 경우 A 또는 B 경기만 남는다. 같은 범위 밖 경기와 다른 모드 경기는 제외된다. C 캐릭터는 제외된다. 빈 목록은 전체다.
3. 중복 (uid,gameId)은 한 번만 집계한다. 캐릭터 선택 중 0경기 캐릭터는 표에 남으며 평균·승률은 null이다. 전체 0경기도 JSON에 NaN/Infinity 없이 반환한다.
4. 게임 순위/피해량 등이 누락된 경우 유효 표본만 평균 계산하며 0으로 조작하지 않는다. wins는 rank=1 수, winRate는 유효 rank 표본 분모다. 순위가 유효한 경기만 있는 기본 데이터에서는 일반적인 wins/games와 같다.
5. 페이지를 바꿔도 summary/characters가 동일하다. match 목록만 달라진다. 겹치는 요청에서 늦게 도착한 이전 응답이 최신 필터 결과를 덮지 않는다.
6. 공식 응답 fixture 기반 어댑터 검증: characterNum 매핑, 큰 ID 문자열, explicit-offset 시간, 무시간대 설정 없음 오류, unknown 모드, malformed 응답, 404/429/5xx/timeout.
7. live 오류가 demo 응답으로 바뀌지 않는다. cache live의 stale 경고, 유효하지 않은 수집의 droppedRecords, 첫 페이지 partial 표시가 보존된다.
8. PostgreSQL을 사용할 경우 별도 연결 가능한 테스트 환경에서 migration과 재수집 upsert 멱등성, 실패 시 이전 데이터 보존을 확인한다. DB가 없으면 실행하지 못했다는 사실을 기록한다.

기본 완료 체크는 TypeScript 검사, lint(구성한 경우), 도메인·API 테스트, 프로덕션 빌드다. 브라우저/HTTP 스모크로 초기 데모, 날짜+모드+복수 캐릭터 선택, 빈 결과, 잘못된 입력, 모바일 폭을 확인한다. 실환경 호출과 실제 DB 통합은 각각 수행 여부를 별도로 보고한다.

## 데모 데이터 요건

서버 키·DB 없이 고정 시드/고정 규칙으로 생성된 샘플을 쓴다. 현재 KST 날짜를 기준으로 최근 60~90일에 분산시키되 한 서버 실행/요청 시점의 기준일을 명시적으로 전달해 hydration 차이를 피한다. 적어도 4개 캐릭터, 일반/랭크, 다양한 승패, 하루에 여러 경기와 0경기 날짜가 있어야 한다. 0경기 캐릭터 선택용 메타데이터도 제공한다. random()으로 새로고침마다 성적이 바뀌면 안 된다. 화면과 API 모두 데모를 명시한다.

## 실제 연동 전 확인

실제 API 연결은 키와 네트워크 허용이 있는 환경에서 검증한다. 아래는 현재 확인된 범위이며, 닉네임 조회와 전적 수집은 아직 완료되지 않았다.

### 2026-10-15 실환경 확인 기록

- Node.js 24.19에서 프록시가 필요한 이 환경은 `NODE_USE_ENV_PROXY=1`로 공식 API에 접근했다. 기존 API 키와 도메인 설정을 유지했고, 대문자 `ER_DATA_SOURCE=LIVE`에서도 라이브 모드가 동작했다.
- 인증된 `/v2/data/Character` 조회로 실험체 메타데이터 91건을 확인했다. `/v2/data/Season`에서 현재 `seasonID=41`을 확인했고, `/v1/rank/top/41/3`도 공식 코드 200으로 응답했다.
- 공식 영문·국문 문서의 닉네임→UID→`/v1/user/games/uid/{uid}` 흐름과 앱의 `query` 파라미터 사용이 일치한다. 이전 대화 도구 출력에 기록된 요청은 `GET https://open-api.bser.io/v1/user/nickname?query=toprain`, 응답은 HTTP 200 및 `{"code":404,"message":"Not Found"}`였다. [재구성 fixture](../src/lib/server/fixtures/nickname-lookup-2026-10-15.json)는 원본 HTTP 덤프가 아니며 요청 시각은 기록되지 않았다. `TopRain`, `TOPRAIN`과 랭킹 응답에 등장한 `페이블`도 닉네임 조회에서 HTTP 200/공식 코드 404를 반환했다. 랭킹 응답에는 UID가 없어 게임 API 호출로 이어갈 수 없었다.
- 확인된 것은 닉네임 조회 실패까지다. 사용자 데이터 상태, 조회 서비스 가용성, 권한·제한 정책 중 어떤 이유인지 확인되지 않았다. 전체 API 장애나 닉네임 부재, 키 재등록 필요성을 이 자료만으로 결론 내릴 수 없다. 문제가 계속되면 키를 제외하고 위 요청 URL·HTTP 상태·공식 코드·메시지를 공급자에 전달해 확인한다.
- 당시 자동 테스트 18개, TypeScript 검사, 프로덕션 빌드는 통과했다. 당시 프로덕션 서버(포트 3001)에서 페이지 HTTP 200, `/api/characters` HTTP 200·`source=live`·실험체 91건을 확인했다. `/api/stats`에 `nickname=toprain`, `startDate=2026-10-01`, `endDate=2026-10-15`, `characterCodes=1,2`를 요청하면 당시 구현은 HTTP 404 `PLAYER_NOT_FOUND`를 반환했으며 데모 응답으로 전환되지 않았다. 현재 구현은 동일한 공식 코드 404를 `UPSTREAM_NOT_FOUND`로 분류한다. 잘못된 날짜는 HTTP 400 `INVALID_QUERY`를 반환했다. 실제 API 키는 확인한 응답 본문과 클라이언트 에셋 17개 어디에도 나타나지 않았다. 실제 전적·필터 결과와 처리량은 UID를 얻지 못해 검증하지 못했다. PostgreSQL은 연결되지 않아 통합 검증을 하지 못했다.

## 후속 기능 범위

로그인·즐겨찾기 계정 동기화, 모든 사용자 상시 수집, 전적 90일 이전 자동 복구, 닉네임 변경 이력 자동 연결, 랭킹/메타 분석, 정밀 RP/MMR 변화, 실시간 경기 추적, 복수 날짜 구간 비교는 후속 범위다.
