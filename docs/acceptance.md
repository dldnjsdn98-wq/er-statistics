# 검증 계획 및 후속 연결 체크

## 자동 검증

도메인 테스트는 고정 시각과 소수의 명확한 경기를 사용한다. 현재 날짜에 따라 결과가 흔들리지 않게 시간을 주입한다.

1. KST 단일 날짜 시작 경계는 포함하고 종료 다음날 자정은 제외한다. 월말·연말·윤년·잘못된 날짜·역전 범위를 검증한다. 실행 머신 TZ=UTC와 다른 TZ에서도 결과가 같다.
2. A와 B를 선택한 경우 A 또는 B 경기만 남는다. 같은 범위 밖 경기와 다른 모드 경기는 제외된다. C 캐릭터는 제외된다. 빈 목록은 전체다.
3. 중복 (uid,gameId)은 한 번만 집계한다. 캐릭터 선택 중 0경기 캐릭터는 표에 남으며 평균·승률은 null이다. 전체 0경기도 JSON에 NaN/Infinity 없이 반환한다.
4. 게임 순위/피해량 등이 누락된 경우 유효 표본만 평균 계산하며 0으로 조작하지 않는다. wins는 rank=1 수, winRate는 유효 rank 표본 분모다. 순위가 유효한 경기만 있는 기본 데이터에서는 일반적인 wins/games와 같다.
5. 페이지를 바꿔도 summary/characters가 동일하다. match 목록만 달라진다. 겹치는 요청에서 늦게 도착한 이전 응답이 최신 필터 결과를 덮지 않는다.
6. 공식 응답 fixture 기반 어댑터 검증: characterNum 매핑, 큰 ID 문자열, explicit-offset 시간, 무시간대 설정 없음 오류, unknown 모드, malformed 응답, 404/429/5xx/timeout.
7. live 오류가 demo 응답으로 바뀌지 않는다. cache live의 stale 경고, 유효하지 않은 수집의 droppedRecords, 첫 페이지 partial 표시가 보존된다.
8. PostgreSQL을 사용할 경우 별도 연결 가능한 테스트 환경에서 migration과 재수집 upsert 멱등성, 실패 시 이전 데이터 보존을 확인한다. DB가 없으면 실행하지 못했다는 사실을 기록한다.

기본 완료 체크는 TypeScript 검사, lint(구성한 경우), 도메인·API 테스트, 프로덕션 빌드다. 브라우저/HTTP 스모크로 초기 데모, 날짜+모드+복수 캐릭터 선택, 빈 결과, 잘못된 입력, 모바일 폭을 확인한다. 실환경 호출과 실제 DB 통합은 각각 수행 여부를 별도로 보고한다.

## 데모 데이터 요건

서버 키·DB 없이 고정 시드/고정 규칙으로 생성된 샘플을 쓴다. 현재 KST 날짜를 기준으로 최근 60~90일에 분산시키되 한 서버 실행/요청 시점의 기준일을 명시적으로 전달해 hydration 차이를 피한다. 적어도 4개 캐릭터, 일반/랭크, 다양한 승패, 하루에 여러 경기와 0경기 날짜가 있어야 한다. 0경기 캐릭터 선택용 메타데이터도 제공한다. random()으로 새로고침마다 성적이 바뀌면 안 된다. 화면과 API 모두 데모를 명시한다.

## 실제 연동 전 확인

실제 API 연결은 키와 네트워크 허용이 있는 환경에서 따로 검증한다. 현재 환경에서는 성공했다고 주장할 수 없다.

- UID/게임 ID 자료형, 공식 오류 envelope와 HTTP status를 실제 응답과 대조한다.
- userGames의 반환 한도, 정렬, 페이지네이션 여부·커서·종료 조건을 공식 계약으로 확인한다. 확인 전에는 partial 유지.
- startDtm 시간대와 일자 경계의 실제 의미를 공급자에 확인하고 ER_API_TIME_ZONE 정책을 결정한다.
- matchingMode 코드, 메타데이터/한국어 이름 연결을 실제 응답으로 확인한다.
- 키별 제한과 Retry-After 동작을 확인하고 앱 호출 간격을 조정한다.
- PostgreSQL migration 적용, 재시작 후 영속 조회, 과거 보관 데이터의 기간 필터를 확인한다.

## 범위 밖

로그인·즐겨찾기 계정 동기화, 모든 사용자 상시 수집, 전적 90일 이전 자동 복구, 닉네임 변경 이력 자동 연결, 랭킹/메타 분석, 정밀 RP/MMR 변화, 실시간 경기 추적, 복수 날짜 구간 비교는 후속 범위다.
